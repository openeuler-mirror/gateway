Prompt Log 存储重构方案

评审稿 · 待确认影响性后实施 2026-11-24 范围：crates/boom-promptlog + 薄接线（boom-main / boom-dashboard） 现状代码基线：writer.rs / query.rs / entry.rs

01现状问题：一个根因，四个症状PROBLEM

现有实现的根本决策是把目录树当索引用（{dir}/{team}/{key_hash}/{phase}_{seq}.jsonl），由此决定了全部四个症状：

① 查询 O(N) 全扫描

  • 必须携带 key_hash + team_alias 才能定位目录，只凭 request_id 无从下手
  • 定位后仍是整个读入解压每个文件、逐行 JSON parse 匹配（scan_dir_for_entry）
  • 感知上"压缩后查不到"——实际是 .gz 被全量解压扫描，慢到形同不可用

② 无老化，磁盘无限涨

  • 全 crate 唯一删除是压缩后删原文件；内容与 boom_request_log 元数据表均无清理
  • 目录树无全局时间序，"按时间删"结构上做不了

③ 过载丢行

  • channel 容量 1024，满即丢弃（慢盘 / OTLP 阻塞时真实发生）
  • "不许阻塞请求"的动机正确，但顺序 I/O 排空能力远大于生产速率，应分层吸收而非丢

④ 小文件森林

  • 每 key 2 个文件独立 gzip：句柄散、写打散、单文件压缩丢掉跨条联合压缩收益
  • 两相位 lockstep 对齐 + 崩溃自愈已需要 6 个测试场景伺候——目录布局带来的意外复杂度

02总体架构：元数据 / 内容分离（split store）ARCHITECTURE

① boom_request_log 已有PG 元数据层：列表 / 过滤 / 统计 / 审计。request_id + instance_id 是 join key，零改动
② 段存储引擎 新建 ★boom-promptlog 内：追加 / 块压缩 / request_id 索引 / 封段。唯一新建组件，~2k 行机制胶水
③ boom-state 心跳注册表 已有多实例寻址：详情请求按 instance_id 代理到持有数据的实例
④ 老化删除任务 新建（薄）保留策略执行：整段 unlink。OTLP exporter（⑤，已有）作为外部平台出口保持不变
请求热路径 ─┬─► boom-audit ──────► PG boom_request_log（元数据行） └─► boom-promptlog ──► 单写者 ─► 追加活跃段 ─(满/到期)─► 封存 + 固化索引 看板 ──列表/过滤──► PG （两条记录靠 request_id 关联） ──点详情──► 行含 instance_id ─► 心跳注册表寻址 ─► 代理到目标实例 ─► 段索引定位 ─► 解压单块 老化任务 ──超期──► 整段 unlink ──► 对应 request_id 详情返回 410 "已被保留策略删除" OTLP ──► 外部采集器（有数据平台的部署方由此消费，双写不冲突）

依赖原则不变：不引入任何新第三方系统；新增第三方库仅 zstd / xxhash / crc 三个原语级 crate。自研部分 = 文件格式 + 点查索引 + 删除循环三件胶水——与 PlanStore=DashMap+机制层、audit=sqlx+PG+表结构同一哲学。段存储不依赖 DB，no-DB 部署模式天然可用。

03核心机制MECHANISM

存储形态：段 → 块 → 记录

SegmentFile（封存后不可变） ├ Header magic | instance_id | start_ts ├ Block×N zstd(多条 JSON 记录拼合, ~2MB) ├ Footer 记录数 | 时间范围 | CRC {seg}.idx request_id→块号·偏移（排序二分）+ bloom
  • 块级压缩：偏移写入时永久固定，封段零额外工作，点查只解压命中块（Kafka batch / Loki chunk 同构）
  • payload 保持现有 PromptLogEntry JSON 原样——schema 不变

写路径：不丢失的分层背压

  • 热路径只做 Arc clone + try_send（现有形态，开销已合格）
  • 内存 channel（字节预算）→ 磁盘 spill → 仅盘满时 drop+计数+告警：把"慢"分层吸收，丢行点从"队列满"退到"磁盘满"
  • 组提交 fsync（默认 interval）：进程崩溃零丢失，掉电窗口 ≤1s（语义可配置）
  • request 入口即写 + response 完成写的两相语义保留（上游挂了也有请求记录）

查询路径：索引定位，O(log n)

  • request_id → bloom 剪枝 → .idx 二分 → 解压一个块 → 返回
  • 不再需要 key_hash / team 提示；压缩数据是一等公民
  • 多实例：看板实例代理到目标实例（instance_id 列已存在）
  • 配套 CLI：list / cat / get / dump --from --to，离线可用（拷走 segments 目录即可，dump 输出与今天 JSONL 同构）

老化：整段删除，O(1)

  • 策略：max_age_days + max_total_gb + 磁盘水位（90% 强删最老段并告警）
  • 封存段不可变 → 删除 = 从 manifest 摘除 + unlink，零碎片整理、零写放大
  • 段自描述（header/footer/CRC）→ manifest 只是缓存，崩溃后扫描目录可重建
  • 配套：boom_request_log 同口径老化，避免元数据悬空；已删 → 410 如实返回
一句话：写路径保留"单写者顺序追加"的正确内核，把"满即丢"换成"内存队列 → 磁盘 spill"；查询从"目录遍历全扫描"换成"bloom + 固化索引定位"；老化从"不存在"换成"整段 O(1) 删除"；检索（PG）与内容（段文件）各归其位。

04关键取舍：为什么不是它们TRADE-OFFS

候选否决理由
SQLite（嵌入式）点查甚至更快，但三个结构错配：老化= DELETE+VACUUM 反复重写全库（"每天一个库文件"绕路 = 重新发明段存储，更差）；压缩非原生（逐条 blob 压缩比差）；WAL 每字节双写；坏页伤全树。B-tree 为"按 key 改/精确删"优化，日志 workload 是"只追加、按时间删"
全进 PGMB 级 blob 的 TOAST/WAL 放大 + vacuum 常年期；no-DB 模式直接不可用
外部平台
（ClickHouse / Loki / S3）		数据路径上最"标准"，但破坏自包含部署底线、看板要跨系统拼接。OTLP sink 已是它的完整实现——有平台的部署方现在就能走，不是本次重构的替代项
嵌入式 KV
（redb / rocksdb）		MB 级大 value 写放大严重；老化由 compaction 驱动，无法整文件删
修补现有布局加索引 → 索引指向会被 gzip/轮转的文件，偏移失效；加老化 → 目录树无时间序；现有 lockstep 对齐治理（6 个测试场景）就是修补成本的实证

业界印证：Loki chunk / VictoriaLogs part / Kafka log segment / ClickHouse part 全部是"时间分区 + 追加文件 + 整文件删除"形态——LLM 网关 prompt log 与它们同构，借形状不借体量。

05影响面清单（评审重点）IMPACT

类别内容
不变 配置项语义（enabled / excluded_* / record_headers / capture_raw_upstream）；两相写入与流式捕获（LoggedStream）；OTLP 双 sink 与 replay；boom_request_log 表结构；dashboard 交互流（列表→点详情）；崩溃自愈能力（形态更简）
改变 磁盘形态：{team}/{key}/*.jsonl(.gz) → segments/*.seg + .idx（裸文件不再 cat 可读，配套 CLI 补偿，dump 输出同构）； 详情端点：key_hash 从必填→可选；过载行为：满即丢→spill 降级；压缩数据查询：全解压扫描→索引定位
新增 promptlog CLI（离线）；旧数据一次性导入工具；老化删除 + 410 语义；私域 YAML 配置段（segment / retention / durability / spill——按三判据全部为本机语义，各实例异构正确）
明确放弃 按目录人工浏览（改由 dump / 查询 API 承载）；不做查询时的 legacy 降级扫描（双路径必然腐化，靠一次性导入收口）

新增决策均为私域 YAML（本机磁盘路径/水位/fsync/段参数），符合配置三域判据，不进 DB、不广播；无 DDL 变更（instance_id 列已存在）。

06迁移与验收MIGRATION

  • 三步走：① 新格式 + 索引查询上线（dashboard 端点 key_hash 转可选）→ ② 旧目录一次性导入（旧文件不动，人工确认后清理）→ ③ 观察期后移除旧写路径
  • 验收：高并发压测断言 dropped == 0（spill 命中率单列计数）；老化删段后 410 语义正确；点查延迟达标（结构上 O(log n) / 单块解压，具体数值以压测为准）；崩溃恢复（尾部截断）
  • 回滚：旧目录在导入后保留至人工确认，期间可回退旧版本读写
  • 规模预估：boom-promptlog ~2–3k 行（格式/索引/查询/老化/CLI/导入）+ dashboard / boom-main 薄接线

07待拍板决策点DECISIONS

决策选项与推荐
「不丢失」的语义边界推荐组提交 fsync（掉电 ≤1s / 进程崩溃零丢）；可选宽松（仅 page cache）或每条 sync（审计级，吞吐代价 1–2 个量级）
老化默认保留期推荐默认 7 天 + 可选容量上限 + 磁盘水位强删（给会自动清理的安全默认，避免上线即无限涨）；可选 30 天 / 默认永久
段文件格式预留推荐自研二进制段起步，manifest 按可导出形态预留（将来接数据平台时封存段可转 parquet，纯增量演进）；若公司终局明确是日志进数仓，可直接选 parquet 起步（引入 arrow 依赖树）
